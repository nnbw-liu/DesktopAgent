# P7 报告：外部仓库基准与优化

> 日期：2026-10-23 · 仓库：`commandlineparser/commandline` @ `b0b0ec9`（tag `v2.9.1`）
> 模型：Qwen3.5-4B（8K Compact）、Qwen3-8B Q4_K_M（32K Full，`/no_think`）、DeepSeek V4 Pro（云端 32K Full）
> 结论：**32K 目标在云端 DeepSeek 上达成（两轮均 7/8）；8K 目标未达成（1/8）**。本地 8B 两轮均 1/8，说明 P7 的差距首先是模型档位，其次才是工具链。

## 1. 做了什么

- 锁定外部仓库与 commit，记录基线：`dotnet build CommandLine.sln` 通过，`netcoreapp3.1` 684 个测试全绿，冷构建约 29s。
- 冻结 8 个任务（T01–T08）：feature / bugfix / tests / refactor / mixed，每个任务带验收命令与隐藏测试。
- 新建隔离评测运行器 `tools/AgentEval`：
  - 从镜像创建临时 git worktree；
  - 每个任务前 `git reset --hard` + `git clean -fd`；
  - 记录输出、工具轨迹、步数、耗时、上下文配置；
  - 在注入隐藏测试前捕获 `git diff`；
  - 注入隐藏测试后执行验收，产物落 `transcript.json` / `changes.diff` / `acceptance.log` / `verdict.json`；
  - 支持 `--only`、`--keep-work` 与宿主回灌。
- Round 1 后按失败类型修 Top 3：
  1. Full 模式改用编码工作流提示词（原先是通用助手提示词，模型经常只输出计划、不调工具）；
  2. `write_file` 拒绝明显缩水的已有文件覆盖（阻止“整文件重写”把源文件截断）；
  3. `replace_text` 失败时给出最接近的源码行，减少盲目重试；
  4. 运行器增加“没有检测到文件修改”回灌，避免模型空口宣布完成。
- Round 2 用同一 commit、同一任务、同一配置重跑。
- 追加云端 DeepSeek V4 Pro 32K Full 两轮：同一 commit、同一任务、同一 15 次工具预算，provider 为 `ds`。

### 1.1 与计划的偏差

- 没有写运行器自身的单测，也没有做假模型 dry-run；运行器通过 smoke + 多轮 8 任务实跑验证。
- 云端 DeepSeek 已同配置双跑（7/8 vs 7/8，差 0）；本地两轮之间夹着修复，不是纯重复性实验。
- 没有统计真实审批次数，评测使用自动审批；审批指标不适用。
- T05 的测试名检查、T07 的私有方法名检查属于实现级约束，放大了失败率；T05 在云端两轮都失败。
- 早期一次运行器版本在回灌判定时漏注入隐藏测试，结果保存在 `eval/results/round1/full-32k-invalid-repair/`，已从基线中剔除，未用于本报告数字。

## 3. 失败分类与根因

| 类别 | 数量（本地 32K R1/R2） | 典型表现 | 根因 |
| --- | --- | --- | --- |
| F6 循环 | 4 / 6 | 同一 `search_files` / `replace_text` / `write_file` 反复调用，直到 15 次上限 | 模型不会从失败信息换锚点；搜索正则过窄；工具失败仍返回 `status=ok`，轨迹难区分 |
| F2 工具误用 | 2 / 1 | 写出不存在的 API、修改错误文件、`apply_patch` 格式错误 | 8B 对外部仓库 API 的 grounding 不足 |
| F5 过早结束 | 1 / 0 | 只输出“已完成”，没有改文件 | 修复前的空完成；Round 2 的 no-edit 回灌已消除该分类 |
| F3 补丁失败 | 归入 F6 | `replace_text old_text` 不匹配、`apply_patch` hunk 不匹配 | 模型把 read_file 的行号/渲染文本当成原文；缺少“最近匹配片段”时只能盲试（Round 2 已补诊断） |
| F4 构建环境 | 0 | 无 | 外部仓库构建稳定；NuGet 仅 warning |

云端 DeepSeek 两轮只有 T05 失败（F6）：三轮共 48 步都在读 `UnParserExtensionsTests.cs` 和查找测试假类型，没有产生 diff；不是构建或补丁失败，而是“测试类任务 + 15 次工具预算”下的定位成本过高。

4B 的 8K Compact 在 Round 1 全部为 F6：上下文只有 8K，模型倾向于重复读同一文件/重复同一搜索，每轮 15 次调用内无法完成定位 + 补丁；Round 2 仅 T02 通过。

## 4. 关键证据

- 8B 默认 thinking 会吃光输出：直接请求 `2+2` 返回 256 token 的 `reasoning_content`、无正文；system 加 `/no_think` 后正常。P7 32K 配置强制 `/no_think`。
- 8B 在 T03 把 1135 行的 `HelpText.cs` 重写成 21 行；T04 把 340 行的 `UnParserExtensions.cs` 重写成 41 行。Round 2 的 shrink guard 拦住了这两类写入，但模型没有转而写出正确补丁。
- T01 Round 2 的工具轨迹显示：`apply_patch` 返回“第 1 个 hunk 未匹配”并给出第 36–59 行上下文，模型仍继续重复同类调用；`write_file` 被 shrink guard 拒绝后，模型没有回到 `replace_text`。
- T08 是本地 8B 在 Round 2 唯一通过的复杂任务：工厂方法小、目标文件明确、隐藏测试只检查公开 API，模型三次续跑后写对。
- 8K 的 T02 在 Round 2 通过（49 步 / 3 轮 / 83s）：这是“无修改回灌”直接救回来的任务；其余 7 个任务都在 50 步左右耗尽 3 轮，失败分类全部为 F6。
- 云端 DeepSeek V4 Pro 在 T01–T04、T06–T08 上大多 16 步完成（一次定位 + 一次补丁），两轮仅 T05 失败；T05 的 3 轮轨迹显示 48 步全部用于读文件/找假类型，没有写入任何测试。
- DeepSeek 的 reasoning_content 不影响工具调用：直接 API 测试能正确返回 `read_file` 的 tool_call；运行器不需要 `/no_think`。

## 6. 推荐与边界

- **当前最适合外部仓库任务的档位**：云端 DeepSeek V4 Pro 32K Full，实测 7/8（两轮）；它能在 16–33 步内完成定位 + 补丁，失败集中在测试类任务的定位成本。
- **本地 8B/32K**：只能做“单文件、公开 API、目标明确”的小改动（1/8）；4B/8K 只适合极短任务（1/8）。
- **不建议**继续用本地 8B 刷 P7 指标；32K 指标已经证明需要 14B–32B 或云端 32K。本机 11GB VRAM 放不下 14B Q4 + 32K KV 的舒适组合。
- **工具链边界**：外部仓库任务的瓶颈不是构建，而是“定位文件 + 生成可应用补丁”；云端模型已经证明工具链可用，剩余问题更偏任务预算与测试类任务。
- **任务设计边界**：T05/T06 指定测试名、T07 指定私有方法名，属于实现级验收；T05 在云端两轮都因此失败，后续应改行为级断言。

## 7. 下一轮 backlog（按影响排序）

1. 把 DeepSeek V4 Pro 双跑 7/8 作为基线，补测 T05 在 20–25 次工具预算下是否通过，区分“模型不会写测试”与“预算不足”。
2. 给 `apply_patch` 增加“按 hunk 上下文自动模糊定位 + 失败时给出可直接复制的候选补丁”，减少本地 8B 的锚点失败。
3. 工具失败返回非 `ok` 状态（或在 trace 中标记 `rejected`），让循环保护和失败分类不再把“被拒绝的写入”当成成功。
4. `search_files` 支持更宽松的字面量搜索（当前正则过窄，`ParserSettings.MaximumDisplayWidth` 搜不到属性行）。
5. 对“只读/测试类”任务提供更明确的文件范围提示（不泄露实现），降低 T05 的定位成本。
6. Full 模式的“无修改回灌”产品化（当前只在评测运行器里），并限制最多 3 次，避免空转。
7. 云端双跑已做；本地配置仍需纯双跑（同一份代码不夹修复）统计方差。
8. 任务 T05/T06/T07 改为行为级验收，去掉测试名/私有方法名要求。
9. 评估把 `write_file` 的 shrink guard 默认打开的产品影响；当前仅靠阈值保护，可能误伤合法删减。
10. 记录真实审批次数、云端 token 成本与 p50；评测的自动审批不能替代产品指标。
