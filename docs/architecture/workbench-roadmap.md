## 1. 一句话定义

**个人工作台 = 一个会做事的智能体（DesktopAgent）+ 一块能把工具软件摆上桌面的壳（DesktopAssembly）+ 若干只负责自己那摊数据的应用。**

| 层 | 角色 | 关键约束 |
| --- | --- | --- |
| DesktopAgent | 理解意图、编排跨应用动作、做所有需要模型的事 | **唯一持有模型凭证的地方** |
| DesktopAssembly | 常驻外壳：托盘、组件宿主、窗口管理、进程管家 | 不保存任何业务数据 |
| 应用 | 各管一份数据，暴露 MCP 能力面 + 桌面组件 | **不持有模型凭证、不写窗口策略、不互调** |

这三条约束不是风格偏好，是这套东西能不能长期活下去的分界线。下面每一条规划都从它们推出来。

## 2. 应用准入规则

工作台最大的风险不是技术，是**应用数量失控**——每个想法都开一个新项目，三个月后没人维护。所以先定入场券：

一个应用要成立，三条必须全满足：

1. **有独立持久数据**（不是别的应用数据的视图）；
2. **有独立后台生命周期**（索引 / 同步 / 目录监控，需要常驻或定时跑）；
3. **有能被 AI 调用的能力面**（MCP），且这个能力面别处给不了。

只满足一条的，做成现有应用的**页面或组件**，不新开项目。

按这条筛一遍你列的清单：

| 想法 | 结论 | 理由 |
| --- | --- | --- |
| 待办 | ✅ 一个应用 | 独立数据 + 独立提醒/重复规则 |
| 日历 | ❌ 不单独成立 | 和待办同一份时间数据，拆开必然出现「待办改了日历不知道」 |
| 知识库 | ✅ 一个应用 | 独立数据 + 独立索引/导入生命周期 |
| 会议纪要 | ✅ 一个应用 | 独立数据（录音/转写/分析）+ 独立长任务；且**会议横切多个项目**，不隶属任何项目（见 [meeting-design](meeting-design.md)） |

> 早期判断曾把会议归入 planner 的模块，理由是「产出都是待办」。那是把**产出归属**误当成**数据归属**——按那个逻辑，凡是能产生待办的东西都该并进 planner。修正见 [meeting-design.md](meeting-design.md) §1。

## 3. 应用清单（v1 只做两个）

```
sdemo.planner   —— 计划：待办 + 日历
sdemo.kb        —— 知识库：个人文档/资料/需求的统一管理与检索
sdemo.meeting   —— 会议：录音、转写、纪要与分析存档
```

### 3.1 `sdemo.planner`：待办与日历合并

**为什么必须合并**：一条待办的 `dueAt` 就是日历上的一个点。分成两个应用，改一遍标题要跨进程通知一遍，冲突处理翻倍，而用户视角里它们本来就是一件东西（「今天要做什么」）。

但**概念要分开**，同库不同表：

| 形态 | 语义 | 能勾完成 | 有起止时间 |
| --- | --- | --- | --- |
| `todo` | 任务 | ✅ | 只有截止点 |
| `event` | 日程 / 占用 | ❌ | ✅ 起 + 止 |

「下午 2 点和张三开会」是 event；「会前把方案发给张三」是 todo。两者可以互相生成（会议 event 自动带一条「准备材料」todo 的模板），但**不混表**——混了以后「完成率」「逾期」这类统计就没法算了。

**对外集成只做 ICS（RFC 5545）**：

- 导出：把 `todo(dueAt)` 与 `event` 导出为 `.ics`，可导入系统日历 / 手机；
- 只读订阅：允许填一个外部 `.ics` URL 或本地文件，定时拉取，**只读镜像**；
- 明确不做：Outlook / Google 双向同步、企业微信 / 钉钉日历。双向同步要 OAuth + 增量同步 + 冲突合并，是另一个量级的工程，等单人多端同步跑通再谈。

### 3.2 `sdemo.kb`：知识库不集成进 DesktopAgent

你问的「集成到 DesktopAgent 还是新开一个 Agent to Agent」，我建议**新开应用，但让它零 AI 凭证**。三个理由：

1. **生命周期不同**。文档库要常驻做目录监控、增量索引、重建、备份。这些挂在一个聊天客户端上，等于让聊天窗口背着另一个应用的定时任务。
2. **消费者不止一个**。工作台的意义就是「多个客户端/AI 共享同一份数据」。知识库将来可能被别的 agent 或脚本查，绑死在 DesktopAgent 里就没有这个能力了。
3. **数据风险半径**。知识库是你的个人资料，混进聊天库意味着一次聊天库迁移或损坏会连累它；分开是各自独立的备份与恢复。

**但「Agent to Agent」这个说法里有个真问题：谁调模型？**

如果 `sdemo.kb` 自己带 provider 配置和 API Key，你会得到：两处密钥、两套额度统计、两次重试策略、两套降级逻辑。这是明确要避免的。

所以定一条原则：**模型凭证只存在于 DesktopAgent，其它应用零凭证。**

知识库因此只负责「存 + 找」，回答由 DesktopAgent 的模型基于片段完成：

```
用户问 → DesktopAgent 调 kb_search（MCP，低风险）
       → 返回片段（带 docId / 位置 / 摘录）
       → DesktopAgent 用自己的模型总结、引用
       → 引用 chip 可跳回原文档
```

检索方案直接复用已验证的中文 FTS5 方案（[workspace-memory.md](workspace-memory.md) §2.2 与 [WorkspaceMemoryIndex.cs](../../src/Storage/SDemo.DesktopAgent.Storage/WorkspaceMemoryIndex.cs) 的 2-gram 预分词）：SQLite `unicode61` 把整段中文当一个 token、`trigram` 又不支持两字查询，这个坑现有代码已经踩过并绕过了，别重踩一遍。

语义检索（embedding）**v1 不做**。理由和现有实现一致：本地 embedding 要带一个模型文件与 ONNX 运行时，收益在「同义改写」这一类查询上，等关键词检索明显不够用了再加。

### 3.3 `sdemo.meeting`：独立应用

录音 → 转写 → 议题/决议/待办候选。三条与别的应用不同的地方：

1. **会议不隶属任何项目**，用 `mtg_topic` 拆分议题，每个议题各自用 URI 指向不同项目的文档/清单——这是它必须独立建模的根本原因；
2. **候选 ≠ 待办**：会议只产出 `mtg_action(candidate)`，转成待办要经 DesktopAgent 中转并由用户在 planner 里审阅；
3. **转写走本地 whisper，不引云端**：会议录音含客户名与报价，默认不上云，也不破坏「应用零凭证」。

完整设计见 [meeting-design.md](meeting-design.md)。

## 4. 跨应用引用与统一搜索

这是工作台和「一堆独立小软件」的区别所在，必须现在就定方式。

### 4.1 引用用 URI，不互相调用

| 动作 | 做法 |
| --- | --- |
| 待办要关联一份需求文档 | 存 `link: "sdemo.kb/doc/{id}"` 字符串，**不调对方接口** |
| 点击这条链接 | DesktopAgent 解析 URI → 调对应应用的 `*_get` → 拿到标题与入口 |
| 应用之间 | **永不直连**（不满足「不互调」约束） |

URI 形如 `sdemo.<appId>/<entity>/<id>`，各应用在自己的 `links` 表里存字符串即可，解析责任在 DesktopAgent——它本来就有模型，能理解「关联到上次那份需求」。

### 4.2 统一搜索 = DesktopAgent 做 fan-out

工作台如果没有「一个搜索框查遍所有应用」，用起来会很碎。但**宿主不能承担这个**（宿主无数据原则），所以由 DesktopAgent 承担：

- 一个「查一下」的意图 → 并行调 `todo_search` / `kb_search` / `calendar_range`
- 各自返回片段 → DesktopAgent 合并、排序、引用
- 每一步都走现有工具结果预算，不额外造一套

这也是 DesktopAgent 在工作台里的定位升级：**从「聊天客户端」变成「总控 / 编排者」**。

## 5. 工具面膨胀怎么办

v1 全部铺开后，模型能看到的工具会变成：

| 来源 | 数量（估） |
| --- | --- |
| 现有内置工具包 | ~20 |
| `sdemo.planner` MCP | 13（[清单](todo-mcp-surface.md#3-工具清单)） |
| `sdemo.kb` MCP | 9–10（[草案](kb-versioning.md#10-mcp-工具面草案s0-补齐)） |
| `sdemo.meeting` MCP | 11（[草案](meeting-design.md#8-mcp-工具面草案)） |

50+ 个工具塞给一个模型，路由准确率会明显下滑——你们现在的小模型评测（[p6-report](../reports/p6-report.md)）已经证明工具数对成功率很敏感。

对策（沿用现有机制，不新造）：

1. 复用「每轮最多暴露工具数」的设置，MCP 工具和内置工具**同池竞争**；
2. 按应用开关：`sdemo.kb` 关掉后它连工具都不出现，不是"暴露但不让调"；
3. 每个 MCP server 可以在 `app.json` 里声明 `toolHints`（例如「查文档时优先 kb_search」），进系统提示时算进技能索引的预算；
4. 高风险工具（删除/清空）**不进默认暴露集**，需要时由用户显式打开或模型调 `search_capabilities` 才浮现。

## 6. 分期规划

| 期 | 内容 | 交付物 | 验收 | 人日 |
| --- | --- | --- | --- | --- |
| **P0** | 契约 | 四份架构文档（已完成） | 字段与错误码无歧义 | ✅ |
| **P1** | 宿主 MVP + spike | DesktopAssembly 最小可用 + Hello Widget | native 组件能显示/拖动/置顶/穿透/多屏还原；Win+D 行为实测出结论 | 5–7 |
| **P2** | Planner v1 | `sdemo.planner`：todo + event + 主窗口 + 组件 + MCP | 手工 CRUD、日历视图、ICS 导出、MCP `todo_list/create/complete` 通 | 10–14 |
| **P3** | DesktopAgent 接入 | MCP client + 审批策略 + 派生卡片采纳 + 跨应用引用 | 聊天里能让 AI 建待办；删除弹确认；引用可跳转 | 5–7 |
| **P4** | KB v1 | `sdemo.kb`：导入 + 索引 + `kb_*` MCP | 100 篇文档导入后关键词检索能命中；引用可跳回 | 10–14 |
| **P5** | 单人多端同步 | outbox + 零服务器导入导出 | 两台机器合并后条目一致、冲突可见 | 3–5 |
| **P6** | 会议应用 | `sdemo.meeting`：录音 + 本地转写 + 议题拆分 + 候选 → planner | 30 分钟会议能产出可审阅的待办候选；跨项目议题能各自挂到对应文档 | 14–20 |
| **P7** | 团队共享 / 新应用 | ACL + 冲突 UI + 审计 | 按需再定 | — |

**P1–P5 合计约 33–47 人日**，单人全职约 **7–10 周**（含 20% buffer）。P6 另算。

工期里最容易低估的是 P2——todo+event+日历视图+ICS+组件+MCP，看着都是小东西，加起来比宿主还重。

## 7. 风险

| # | 风险 | 缓解 |
| --- | --- | --- |
| R1 | 应用数量膨胀，维护铺开 | §2 准入规则写进文档，新应用先过三问 |
| R2 | 模型凭证分散到各应用 | 「零凭证」原则；真要离线自主推理时再引入网关，不提前做 |
| R3 | 工具面膨胀导致路由退化 | §5 四条对策，复用现有暴露上限 |
| R4 | 待办+日历合并后模块变大 | 同库不同表，接口按 `todo` / `event` 两套分开，别做成一个万能实体 |
| R5 | 知识库索引成本失控（文档多、重索引慢） | 增量索引 + 索引状态可见；复用现有整库重建的自愈思路 |
| R6 | 跨应用引用变成隐式耦合 | 只允许 URI 字符串，禁止应用直连；解析责任单点在 DesktopAgent |
| R7 | 工作台没有"统一入口"，用起来碎 | P3 就把「查一下」的 fan-out 做出来，别等到最后 |
| R8 | 会议录音挤占磁盘 / 误上云 | 默认本地 whisper + 录音 90 天保留 + 设置页显示占用；云端 ASR 只能由用户显式开启并标红提示 |
| R9 | 本地转写质量与耗时不可控 | 模型档位对用户可见（small / medium），转写是后台任务、可取消；质量不足时再评估云端例外条款 |
