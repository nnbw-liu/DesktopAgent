# 智能模型路由

> 目标：让同一个 DesktopAgent 在「便宜模型够用」的轮次上省钱，在「必须强模型」的轮次上不掉质量；
> 同时把选择权留给用户——可以全自动，也可以由用户给每类任务指定模型。
>
> 状态：✅ 2026-10-25 首版落地（规则 / 混合 / 总控 + 设置页 + 聊天室「自动选择」）。
> 代码：`ModelRouter`、`ModelTaskClassifier`、`LlmModelRoutingAdvisor`、`ModelRoutingSettings`。

## 1. 为什么不是「一个模型打天下」

DesktopAgent 同时支持 8K 本地小模型和 128K / 200K 云端模型。真实使用里，一天大多数请求是
「解释一下这个报错」「这个文件在哪」「改一个字段」；少数才是「跨模块重构」「排查根因」。
如果默认永远用最强模型，简单请求按前沿价格计费；如果默认永远用小模型，复杂任务会反复失败。

模型路由不是让模型「更聪明」，而是**让每一轮匹配到足够好且足够便宜的那一档**。

## 2. 市面上的做法（2026-10 调研）

| 方案 | 判断方式 | 用户可配置 | 对 DesktopAgent 的启发 |
| --- | --- | --- | --- |
| [OpenRouter Auto Router](https://openrouter.ai/docs/guides/routing/routers/auto-router) | 轻量分类器分出 ~30 种任务，再按社区真实消费排名 + `cost_tier` 选模型 | 允许 / 排除模型、成本档、`session_id` 粘性 | 「任务分类」和「成本档」分开；会话粘性避免每轮换模型 |
| [Cursor Router](https://cursor.com/en-US/blog/how-cursor-router-works) | Compass 复杂度打分 + 领域 / 任务 / 修饰符分类，按各模型真实表现与预算组合 | Auto Balance / Auto Intelligence 两档 | 复杂度先决定「要不要升级」，再看「升级到谁」；按每次交付成本评估 |
| [GitHub Copilot Auto](https://github.blog/changelog/2026-07-01-copilot-cli-auto-model-selection-routes-based-on-task/) | 推理 / 代码生成 / 缺陷诊断 / 工具编排等维度 + 可用性与健康度 | `/model` 随时切回固定模型 | 路由要尊重策略与可用性；用户必须能一键接管 |
| [LiteLLM Auto Router](https://docs.litellm.ai/docs/auto_router/) | 四档 SIMPLE / MEDIUM / COMPLEX / REASONING；启发式或 LLM 分类器 | 每档指定模型、分类器、会话粘性、上下文升级 | 档位是用户能理解的配置单位；失败回落与上下文升级是必备 |
| [Claude Code `opusplan`](https://code.claude.com/docs/en/model-config) | 固定模式：Plan 模式用 Opus，执行用 Sonnet | `/model` 别名 | 「阶段」本身也能作为路由信号，不一定每轮都要分类 |
| [RouteLLM / FrugalGPT 等研究](https://github.com/lm-sys/RouteLLM) | 二分类强弱模型 / 级联升级 | 阈值 | 简单场景二分类就够；级联（先便宜，失败再升级）可作后续 |

共同点：

1. **先判断难度 / 任务类型，再选模型**，而不是按输入长度拍脑袋。
2. **有明确的成本档或用户映射**，路由不是黑盒。
3. **失败必须可回落**：分类器不可用、模型不可用、上下文装不下，都不能让请求失败。
4. **会话粘性 / 缓存边界**很重要：频繁换模型会把提示缓存打掉，省下的钱可能又还回去。
5. **用户始终能接管**：一键固定模型，路由只是默认值。

## 3. 本项目的取舍：判断与决策分离

DesktopAgent 是 BYO provider / BYO key 的本地应用，没有云端真实消费排名，也不应该把用户 prompt
默认发给第三方路由服务。因此首版采用「**规则优先、模型可选、映射由用户定**」：

```text
用户输入 + 会话长度 + 工具包 + 手选技能
        │
        ▼
┌──────────────────────────────┐
│ ModelTaskClassifier（成本 0）│  闲聊 / 简单 / 代码 / 复杂 + 置信度 + 复杂度
└──────────────┬───────────────┘
               │ 模式
   ┌───────────┼────────────────┬─────────────────┐
   ▼           ▼                ▼                 ▼
 关闭        规则             混合              总控
固定模型   规则→映射      不确定才问路由模型   路由模型直接选
                            →用户映射          候选清单内
   └───────────┴────────────────┴─────────────────┘
               │
               ▼
┌──────────────────────────────┐
│ 候选过滤：窗口 / 工具能力 / 成本偏好 │
│ 回落：映射 → 兜底 → 当前模型 → 任一候选 │
└──────────────────────────────┘
```

### 3.1 四种工作方式

| 模式 | 额外请求 | 判断 | 选模型 | 适合 |
| --- | --- | --- | --- | --- |
| 关闭 `Off` | 0 | — | 用户手选 | 想完全掌控成本 / 本地模型 |
| 规则 `Rules` | 0 | 本地关键词 + 长度 + 工具信号 | 用户「任务 → 模型」映射 | 默认推荐；可预测、零延迟 |
| 混合 `Hybrid` | 仅规则置信度 < 阈值时 1 次 | 路由模型只判任务类型 | 用户映射 | 想更准，但不想让模型乱选模型 |
| 总控 `Model` | 每轮非闲聊 1 次 | 路由模型判类型 + 直接点名模型 | 候选清单内，模型自己选 | 想让模型总控；适合模型多、差异大 |

### 3.2 任务分类

| 类型 | 信号（首版规则） | 典型请求 |
| --- | --- | --- |
| `Chat` | 短寒暄 / 致谢 / 身份，且无代码形状 | 「你好」「谢谢」 |
| `Simple` | 概念性提问、未命中工程信号、短问答 | 「解释一下什么是依赖注入」 |
| `Code` | 代码 / 文件 / 构建 / 测试 / 报错词、文件扩展名、代码围栏、明确动手指令 | 「帮我改一下 Program.cs」 |
| `Complex` | 架构 / 重构 / 迁移 / 根因 / 多文件 / 长输入 / 会话 >12K token | 「重构整个项目的路由并排查性能」 |

规则故意保守：默认 `Simple` 的置信度只有 `0.45`，因此混合模式会对「拿不准」的请求再问一次；
明确的闲聊 / 代码 / 复杂信号置信度在 `0.7–0.95`，不会浪费路由调用。

### 3.3 候选与护栏

路由模型永远不能绕过宿主：

- **只看得到候选摘要**：provider id / 名字、模型 id、窗口、是否支持工具、价格、用户映射；
  看不到文件内容、工具实现、API Key。
- **模型名会被二次校验**：编造的模型 / provider 直接丢弃；只给任务类型时按用户映射选。
- **窗口护栏**：估算输入超过候选窗口时跳过它；全部装不下时选窗口最大的，再交给上下文层压缩 / 裁剪。
- **工具护栏**：代码 / 复杂任务优先排除明确不支持工具的模型。
- **成本偏好**：只影响候选排序与提示（省钱 / 均衡 / 质量），不覆盖用户的显式映射。
- **超时**：默认 8 秒，可配 1–60；超时、网络错误、JSON 非法、空建议一律回落规则。

### 3.4 回落链

```text
路由模型失败 / 超时
  → 规则分类
  → 用户为该类任务配置的模型
  → 兜底模型
  → 当前聊天室模型
  → 任一可用候选（窗口最大的）
```

任何一层失败都不会让消息发不出去；`ModelRoutingDecision.Source` 会标记 `Fallback`，界面可解释。

## 4. 配置与优先级

聊天室 / 工作区可以覆盖「是否自动」，全局设置决定路由策略与映射。

```text
聊天室 AutoModelRouting
  > 工作区 AutoModelRouting
  > 全局 ModelRouting.Mode（Off 是总开关）
```

- 全局 `Mode = Off`：所有聊天室固定模型，即使聊天室记着「自动」也不路由。
- 全局 `Mode != Off`：聊天室显式为 `false` 的固定；`null / true` 跟随自动。
- 旧会话如果已经显式选过模型（没有 `AutoModelRouting` 标记），按固定模型处理，不会被全局开关悄悄换掉。
- 聊天室模型选择器里的「自动选择」写入 `AutoModelRouting = true` 并清空固定 provider/model；
  手选一个模型写入 `false` 并固定该组合。
- 一轮只路由一次：本次发送内的宿主追问、工具循环、溢出重试都复用同一个模型。

设置项（`settings.json` 的 `modelRouting` 节点）：

```json
{
  "modelRouting": {
    "mode": "Hybrid",
    "routes": [
      { "task": "Simple",  "providerId": "local",  "modelId": "qwen3.5-4b" },
      { "task": "Code",    "providerId": "deepseek", "modelId": "deepseek-chat" },
      { "task": "Complex", "providerId": "deepseek", "modelId": "deepseek-reasoner" }
    ],
    "defaultProviderId": "deepseek",
    "defaultModelId": "deepseek-chat",
    "routerProviderId": "local",
    "routerModelId": "qwen3.5-4b",
    "routerTimeoutSeconds": 8,
    "stickySession": true,
    "respectContextWindow": true,
    "costPreference": "Balanced",
    "advisorThreshold": 0.65
  }
}
```

## 5. 会话粘性与缓存

切模型会让服务端提示缓存失效，尤其对长系统提示 + 工具 schema 的 Agent 场景影响明显。
首版做「同会话、同任务类型、同配置」粘性：

- 30 分钟内，任务类型不变则沿用上一轮模型（`Source = Sticky`）。
- 任务类型变化、路由配置变化（映射 / 模式 / 成本偏好 / 兜底模型）、用户手选模型
  都会让粘性失效。
- 缓存键不包含完整对话内容，因此「同类型新任务」也会粘住；这是有意的成本取舍，
  避免每轮在代码模型和复杂模型之间来回跳。
- 输入框预览只跑免费的规则判断（`AllowAdvisor = false`），不会因为打开一个聊天室就调用路由模型；
  真正发送时才按所选模式完整路由一次。

## 6. 与现有组件的关系

| 组件 | 关系 |
| --- | --- |
| `TurnClassifier` / `CapabilityRouter` | 仍负责「要不要工具 / 要哪些工具」；模型路由只决定「用哪个模型」，在其之前运行 |
| `AgentModeResolver` | 路由后用目标模型的窗口 / 工具能力重新判定 Full / Compact |
| `ContextBuilder` | 用目标模型的 profile 重新计算预算；长上下文可能触发压缩 |
| `SummaryModelId` / `RoutingModelId` | 模型路由模型优先用 `modelRouting.router*`，其次摘要模型，最后当前模型 |
| `IModelRouter` | 新入口；聊天室预览与发送共用，粘性避免重复调用 |

## 7. 失败语义

| 失败 | 行为 | 用户可见 |
| --- | --- | --- |
| 路由模型超时 / 网络错误 | 回落规则 | 模型选择器的悬浮说明显示「兜底」/ 理由 |
| 路由模型输出非法 JSON | 回落规则 | 同上 |
| 模型点名不在候选 | 丢弃模型，保留任务类型，按映射选 | 理由保留模型给的原话 |
| 映射模型已删除 | 兜底 → 当前模型 → 任一候选 | 理由「映射的模型不可用，已回落」 |
| 上下文装不下候选 | 跳过；全部装不下选最大窗口 | 上下文层继续压缩 / 裁剪 |
| 设置文件里没有 `modelRouting` | 默认 `Off`，旧行为 | 无 |

## 8. 评测与观测

首版已记录在 `ModelRoutingDecision`：

- `Task` / `Source` / `Reason` / `Confidence` / `Complexity`
- 消息落库仍保存实际 `ProviderId` / `ModelId`，界面消息底部直接显示模型名。

建议下一步补 `tools/model-routing-eval`：

1. 固定 40–60 条请求，人工标注期望类型与可接受模型集合。
2. 跑 `Rules` / `Hybrid` / `Model` 三档，记录：类型命中率、映射命中率、路由调用次数、
   平均额外延迟、估算成本、回落率。
3. 做 shadow eval：同一请求同时记录「规则选择」和「路由模型选择」，不真正切换，先看差异。
4. 线上指标：每类任务的失败 / 追问率、切模型次数、缓存命中、每次成功任务成本。

## 9. 已知边界

1. **没有学习型路由器**：首版是规则 + 一次 LLM 分类，不训练用户历史偏好；也没有真实消费排名。
2. **规则对中文同义改写不鲁棒**：复杂 / 代码信号是关键词 + 形状，后续可用 embedding 或路由模型兜底。
3. **成本偏好只影响候选顺序**：没有按预算动态优化，也不会因为「这个月快超支」自动降档。
4. **没有级联升级**：不会「小模型失败后自动换大模型重试」；这需要与内循环 / 验证门结合，首版不做。
5. **路由模型本身也花钱**：混合 / 总控模式每轮多一次小模型调用；闲聊与高置信度规则会跳过。
6. **未做真实 A/B**：首版验证的是分类与回落逻辑（单测 + 构建），不是任务完成率提升。

## 10. 后续路线

- **阶段路由**：Plan 阶段用强模型，执行阶段用便宜模型（参考 `opusplan`）；与 `todo_write` / 内循环结合。
- **失败升级**：验证失败 / 连续工具失败时，下一轮自动升一档（参考 LiteLLM stall escalation）。
- **预算路由**：按日 / 按会话成本上限，自动在成本档之间移动。
- **影子评测**：先记录不切换，积累「规则 vs 模型」差异后再开总控。
- **模型能力标签**：在 `ModelEntry` 上增加用户可编辑的 tags（fast / code / vision / reasoning），
  让规则不必依赖模型名猜测。
