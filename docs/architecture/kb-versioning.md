## 1. 先厘清分工线：零凭证 ≠ 零智能

之前说 `sdemo.kb`「只负责存和找」，容易被读成「它是个文件柜」。不是。分工线在**要不要调模型**，不在**要不要动脑子**：

| 归 KB（确定性算法） | 归 DesktopAgent（需要判断/写作） |
| --- | --- |
| 版本链、块级 diff、内容寻址 | 「这次改动到底改了什么意图」的自然语言摘要 |
| FTS 分词与索引、查询路由 | 回答用户问题、跨文档归纳 |
| 引用与影响面反查 | 「哪些待办该跟着改」的建议 |
| 冲突检测（多端） | 冲突的语义裁决 |

一条判定口诀：**能写成确定性代码的，全在 KB；要"看懂"的，全在 DesktopAgent。** 模型凭证只在前者那边，所以后者不能出现在 KB 里。

## 2. 数据模型：实体 + 版本链 + 块

不按「文件」建模，按「实体」建模。五个概念：

| 概念 | 表 | 说明 |
| --- | --- | --- |
| 文档 | `kb_doc` | 稳定身份（UUIDv7）、`kind`（note / reference / requirement / decision）、`current_version_id` |
| 版本 | `kb_version` | 不可变；`seq`、`parent_version_id`、`content_hash`、`author`（user / ai / import）、`reason` |
| 块 | `kb_block` | 版本的内容切分：标题 + 段落，每条有 `content_hash` |
| 变更 | `kb_change` | 一次版本之间的差异：`add` / `remove` / `replace` + `rationale` + `rationale_source` |
| 引用 | `kb_link` | 指向别处的字符串 URI（`sdemo.planner/todo/{id}`） |

三条关键设计：

1. **内容寻址**：块正文按 `content_hash` 存一份（`kb_blob`），版本只引用块 id。50 个版本不是 50 倍存储——改一段只多一份块。
2. **块粒度**：切成「标题 + 段落」，不是行。需求文档是散文，行级 diff 全是噪音；整篇又没法说清"哪一句变了"。段落是唯一同时适合人读和机器算的粒度。
3. **DAG 而非直线**：`parent_version_id` 允许分叉。多端离线编辑时两端各自产生新版本，合并时保留两支、标记分叉，而不是丢一个（见 §7）。

## 3. 一次改动的完整走查

你说的场景：需求先是 A，然后加 B，再把 A 改成 D。

| 时点 | 动作 | 版本 | 存储变化 | 变更记录 |
| --- | --- | --- | --- | --- |
| T1 | 写需求 A | `v1`（根） | 块 `b1`(标题) `b2`(A 正文) `b3`(验收) | — |
| T2 | 添加 B | `v2` ← `v1` | 新增 `b4`(B)；`b1`~`b3` **复用**，不复制 | `add b4`，reason「补充 B 场景」 |
| T3 | A 改成 D | `v3` ← `v2` | `b2` 的 hash 变（`b2→b2'`）；`b1` `b3` `b4` 复用 | `replace b2`，`before=A` `after=D`，reason「原方案不可行」 |

要点：

- **一个版本只改它真正改过的块**，其余引用旧 id。存储增量是 O(改动量)。
- `kb_change.before_text` / `after_text` 直接存，是为了**不依赖再算 diff** 就能回答"以前写的是什么"——历史版本可能被清理，但变更记录永久保留。
- `content_hash` 相同 ⇒ 判定"没改"，直接跳过建版本。所以自动保存不会产生版本洪水。

## 4. 差异怎么记

三层，各自解决不同问题：

| 层 | 谁算 | 产出 | 用途 |
| --- | --- | --- | --- |
| 块级 diff | KB（确定性） | `added` / `removed` / `replaced` 的块列表 | 结构、影响面、增量索引 |
| 块内 diff | KB（Myers / patience） | 词级增删，供界面高亮 | 人读「这一句哪里动了」 |
| 变更理由 | 用户 / AI / 会议 | `kb_change.rationale` + `rationale_source` | 追溯「为什么改」——**这才是最值钱的字段** |

关于「为什么改」的采集，三个入口都要接：

1. 用户在 KB 主窗口保存时填一行「这次改了什么」（可空，不强制）；
2. AI 改文档时，由 DesktopAgent 在审批弹窗里给出建议理由，用户确认；
3. 会议纪要里抽出的决议，直接落成一条带理由的变更。

**命名修订**：`kind=requirement` 的文档强制语义版本（`v1.0 / v1.1 / v2.0`），普通笔记只保留自动版本。原因：需求要对外引用，"第 3 版"必须能说清；笔记不需要。

自动保存的合并窗口：同一个人 5 分钟内的连续编辑合并成一个版本，避免一次输入产生 20 个版本。

## 5. 差异怎么向量化：结论是**不向量化差异**

直接把 "A → D" 这种 diff 文本做 embedding 是个坏主意，三个原因：

1. **它不是自然语言**。diff 是带标记的对照文本，嵌入后落在语义空间里没有意义的位置，反而污染索引。
2. **它回答不了用户真会问的问题**。人问的是「现在怎么规定的」「以前是怎么写的」「为什么改成 D」，不会问「A 到 D 的差异是什么」。
3. **它会被重复嵌入**。同一处改动在多个版本里出现，产生大量近似向量。

正确做法：**差异是结构化事实，进索引的只有"块"。**

三个索引面，按查询意图分开命中：

| 索引面 | 内容 | 典型查询 | 召回策略 |
| --- | --- | --- | --- |
| A. 当前态 | `current` 版本的块 | 「部署流程现在是什么」 | 默认只查这层 |
| B. 历史态 | 旧版本块，标 `superseded` | 「之前是怎么写的」 | 只在显式查历史时召回，且降权 |
| C. 变更事实 | `kb_change` 行 + `rationale` 文本 | 「为什么把 A 改成 D」 | SQL 过滤（文档/时间/作者）+ rationale 走 FTS |

查询路由由 KB 自己判（关键词触发，不调模型）：

| 用户问法里出现 | 路由到 |
| --- | --- |
| 「现在 / 当前 / 最新」 | A |
| 「以前 / 之前 / 原来 / 第几版」 | B（含 A 的前身） |
| 「为什么 / 谁改的 / 什么时候改的」 | C |
| 「影响 / 哪些要跟着改」 | 引用反查（§6），不走向量 |

## 6. 向量化的正确粒度（后续再加）

真要上语义检索时，只嵌**块**，不嵌文档、不嵌 diff：

- 一张 `kb_vector(block_id, content_hash, model, vec)`；
- **按 `content_hash` 复用**：块没变就不重嵌。这是块模型最大的回报——改一段，只重嵌一段，不是整篇。
- 模型版本单独一列：换 embedding 模型时按 `model` 隔离，不污染旧向量。
- 失效判定用 hash，不用时间戳：内容寻址天然幂等。
- 存储：SQLite 扩展（如 `sqlite-vec`）或旁挂一个小向量文件，先不引独立向量库。

v1 落地仍然只做 FTS5（复用 [workspace-memory.md](workspace-memory.md) §2.2 的 2-gram 预分词），向量留到「关键词明显不够用」再上。

## 7. 追溯与影响面：引用必须带版本

引用不能只存 `docId`，必须存 `docId@versionId#blockId`：

```
sdemo.kb/doc/01H…@v3#b2'
```

有了这三段，就能回答两个高价值问题：

1. **这条待办基于哪一版哪一段**——点开能跳到原文位置；
2. **文档改了，哪些东西过期了**——反查所有引用该 `blockId` 的记录；若该块在当前版本已不存在或 hash 变了，标记为「来源已变更，建议复核」。

这就是你说的"A 改成 D"之后真正要解决的问题：**不是记录差异，而是知道差异影响了谁。** 复核动作本身交给 DesktopAgent（它有模型，能判断「待办里写的验收标准是否还成立」），KB 只负责给出「受影响的清单」。

## 8. 与多端同步的关系

版本链是 append-only 的，天然可合并：

- 两端各自产生 `v3a`、`v3b`，`parent` 都是 `v2` → 保留两支，标「已分叉」，由用户或 DesktopAgent 裁决合并（合并动作再产出一个 `v4`，`parent` 指向两位）。
- 块级内容寻址让合并更便宜：相同块自动复用，冲突只剩「同一块被两边改成不同内容」这一种。
- `kb_change` 不参与同步（它是版本的派生物，可由两端各自重算）——少同步一张表就少一类冲突。

## 9. 存储与保留

| 数据 | 保留策略 |
| --- | --- |
| `kb_blob` | 永久；按 hash 去重，块被所有版本丢弃后才可回收（引用计数） |
| `kb_version` | `kind=requirement` 全留；普通笔记保留最近 30 版 + 所有命名修订 |
| `kb_change` | 永久（体积小，且是追溯的唯一依据） |
| 原文导入件（PDF / docx） | 保留原件，随文档删除（走回收站 7 天） |

导入复用现有能力：`IOfficeAttachmentExtractor` / `IPdfAttachmentExtractor`（[Contracts](../../src/Contracts/SDemo.DesktopAgent.Contracts/Abstractions/)）已经能抽文本，导入即建 `v1`（`author=import`），重新导入同一文件则按块 hash 自动算 diff。

## 10. MCP 工具面草案（S0 补齐）

| 工具 | 风险 | 审批 | 说明 |
| --- | --- | --- | --- |
| `kb_search(query, scope)` | 低 | 否 | `scope` = `current` / `history` / `both` |
| `kb_get(docId, version?)` | 低 | 否 | 取正文与块 id |
| `kb_outline(docId)` | 低 | 否 | 章节与块结构，供引用定位 |
| `kb_diff(docId, from, to)` | 低 | 否 | 结构化变更（块级 + 词级） |
| `kb_changes(docId?, since?)` | 低 | 否 | 变更事实流，含理由 |
| `kb_refs(docId)` | 低 | 否 | 谁引用了它 / 它引用了谁；影响面清单 |
| `kb_create(kind, title, blocks)` | 中 | 否 | 建文档与 `v1` |
| `kb_update(docId, ops, rationale, expectedVersion)` | **高** | **总是** | AI 改个人资料，误改代价高，必须确认 |
| `kb_annotate(docId, versionId, summary)` | 低 | 否 | 写「这次改动意味着什么」；`summary_author=ai` |

`kb_update` 的 ops 用块级操作（`add` / `replace` / `remove` + `blockId`），**不要**让模型提交整篇正文——整篇提交会让 diff 失效、也会让「只改一句」变成「重写全文」。

## 11. 边界与非目标

| 不做 | 原因 |
| --- | --- |
| 向量化 diff 文本 | 见 §5，污染索引且答非所问 |
| Git 级能力（分支/变基/cherry-pick） | 个人资料不需要，DAG 只用来处理多端分叉 |
| 整篇正文提交式更新 | 会摧毁块级 diff 与增量索引 |
| KB 内部调模型做摘要 | 违反零凭证原则；摘要由 DesktopAgent 写回 |
| 多文档自动聚类/知识图谱 | 收益不确定，先把版本与追溯做扎实 |
