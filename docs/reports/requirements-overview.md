## 1. 产品总目标

一句话：**用户用自然语言提需求，Agent 在本机仓库里读代码、改代码、跑构建/测试、展示 diff，失败后自我修正，直到验证通过；长会话不爆上下文，改动可审阅、可回滚。**

判定“可用”的五条（来自 `vibe-coding-roadmap.md`）：

1. 50+ 轮长会话在目标模型上不因上下文超限失败；
2. 能在真实仓库完成“加开关 / 修 bug / 补测试”；
3. 以补丁编辑为主，有 diff 审阅，误改可撤销；
4. 改完能自己跑构建/测试，单次循环 p50 ≤ 20 秒；
5. 8K 上下文的模型能完成简单任务，不需要用户手工裁历史。

## 3. 没做 / 没做完的，以及原因

### 3.1 明确列为“本期不做”（范围裁剪）

| 项 | 为什么不做 |
| --- | --- |
| 多 Agent 编排、子任务并行 | 单 Agent + todo 已能覆盖当前任务；多 Agent 的调度、冲突、成本都未验证 |
| LSP / 符号索引 / 语义搜索 | 文本搜索 + 读文件已够用；LSP 集成成本高，收益要等仓库规模更大 |
| 向量库 RAG | 知识库先用 FTS5 关键词；语义检索留到后续，避免过早引入 embedding 依赖 |
| 云端沙箱 / 远程 / 容器执行 | 本期只做本机隔离；云端涉及部署、网络与数据合规 |
| 移动端编码 | Android 只有 UI，沙箱不可用；本期不做移动端改代码 |
| 自动提 PR、git 写操作（提交/推送/切分支） | 安全边界；直跑白名单只允许只读 git |
| 语法高亮 | 外围体验，不影响任务完成；Markdig 不内置 |
| 按任务难度自动切模型 | P6 明确留到下一周期；先做“手动/自动档位” |
| 终端 UI / 交互式 shell / 逐行流式输出 | MAF 工具结果是一次性返回；交互式终端与当前审批模型冲突 |
| 复杂计划 DSL / 依赖图、长周期后台任务 | todo 已够；后台任务在关闭应用后无法保证 |
| 模型微调 / LoRA、本地推理引擎、多模态 | 走 OpenAI 兼容端点即可；微调与多模态不是当前瓶颈 |
| 插件 native / 工具型 / MCP / 市场 / UI 插槽 | v1 只做声明式“技能 + 参数 + 输出”；触发条件（需要读数据库、调私有 API、分发）还没到 |

| 7B / 32K 小模型档位 | ❌ 未测 | 本机只有 4B 端点；4B 已到 3/5，但不能据此宣称 7B/32K 达标 |

| M4 的 8K 长任务回归 | ⚠️ 未实测 | 本机未加载 8K 模型，没重跑 T01–T08；“不低于 M1”目前只是代码层承诺 |
| P7 的 8K 目标（≥3/8） | ❌ 1/8 | 4B + 8K + 15 次工具预算，在外部仓库定位成本过高；报告判断“首先是模型档位，其次才是工具链” |
| P7 本地 32K（≥5/8） | ❌ 1/8 | Qwen3-8B 对未见过仓库的 API grounding 不足，补丁锚点找不到后循环 |
| P4 冷启动 ≤60s | ⚠️ 未单独测 | 验证仓库已 restore / 编译；要清 obj 或干净 clone 才能证明 |
| Win10 Home 手工验收 | ❌ 未做 | 本机没有 Win10 Home 环境 |
| Windows Sandbox 真机 e2e | ⚠️ 部分 | 自检通过，但 VM 内 stdout 读不到（P2）；且仅 Pro / Enterprise / Education 可用 |
| Android 构建 / 运行 | ⚠️ 按需 | 需要 JDK 17 + Android SDK；默认关闭目标，避免 restore 失败 |

### 3.3 安全 / 风险取舍，主动不做

| 项 | 原因 |
| --- | --- |
| NuGet 缓存对 AppContainer 的只读 ACL 映射（P4 4.7） | 要给用户目录放宽 ACL，风险大于收益；改为宿主预 restore + 沙箱内 `--no-restore` |
| 目录递归删除（沙箱变更） | 防误删；只支持文件删除进回收站，目录删除明确不支持 |
| PDF 扫描件 OCR | 沙箱无网络、只读 input；OCR 引擎接入与安全评审未做；`ocr=true` 明确拒绝而不是悄悄退化 |
| AppContainer 内相对路径删除 / 重命名 | PowerShell 当前目录是 `SDEMO:` PSDrive，`Remove-Item` / `Rename-Item` 会 Access denied；回归用例暂时 Skip |
| 插件文本的信任边界 | 第三方插件等于提示词投毒面；v1 只支持本地目录安装 + 首次隐私确认，不做签名/市场 |
| 删除冲突整批中止 vs 跳过 | 写入冲突整批中止；删除冲突按文件跳过（避免一个删不掉导致全批失败） |

### 3.4 代码完成，但缺真机 / 端到端验收

| 项 | 现状 | 影响 |
| --- | --- | --- |
| M1 的 30 工具 / 8K 真机压测 | 只有单测与集成测试口径 | “工具段 ≤1.5K”在真实 30 工具下未采样 |
| M2 的 20 技能真机注入 | 只有单测（20 条长描述 ≤400 token） | 真实技能库的词表与命中率未验证 |
| M3 的 20 条归档端到端跳转 | 单测覆盖索引/检索/分页/引用；UI 跳转未手工点 | 引用 chip 的真实交互未验收 |
| P1 / P2 的 UI 像素级走查 | 构建 + 启动冒烟通过，没有 bUnit / 截图比对 | 占用环、分隔线、pin、菜单的视觉回归只能靠手动 |
| P5 的验证徽标点击、自动续跑端到端 | 逻辑与构建通过；没有假模型集成测试 | 真实 UI 里递归/并发风险未排除 |
| P7 运行器自身单测 / 假模型 dry-run | 只靠 smoke + 多轮 8 任务实跑 | 运行器回归没有自动化保护 |
| 真实审批次数 / 云端 token 成本 | 评测使用自动审批 | P7 的“每任务审批 ≤2”没有产品实测；成本未统计 |

### 3.5 指标未达标（不是没做，是没达到）

| 指标 | 目标 | 实测 | 原因 |
| --- | --- | --- | --- |
| P7 8K 任务成功率 | ≥3/8 | 1/8（4B） | 8K 窗口 + 外部仓库定位 + 15 次预算；模型能力优先 |
| P7 本地 32K 成功率 | ≥5/8 | 1/8（8B） | 8B 的 API grounding 与补丁锚点能力不足；云端 32K 已 7/8 |
| P7 内循环 p50 | ≤20s | 云端 32–145s；本地 32K 42–460s；8K 83–249s | 指标定义含模型推理时间，与 P4 的“热构建/测试 6.7s”不是同一口径 |
| P6 工具调用解析失败率 | ≤10% | 未达标（`apply_patch` 仍常见失败） | 靠 `replace_text` 兜底，没有把格式失败率降下来 |
| P6 7B / 32K | ≥3/5、≥4/5 | 未测 | 无端点 / 无显存 |

### 3.6 产品化 / 体验缺口

| 项 | 现状 | 为什么重要 |
| --- | --- | --- |
| Full 模式“无修改回灌” | 只在评测运行器里，产品里没有 | 模型空口说“已完成”时，产品不会自动追问；最多 3 次的策略也没落地 |
| `write_file` shrink guard | 评测里拦“整文件截断”，默认未开 | 默认开可能误伤合法删减；不开又可能把源文件写坏 |
| 路由模型独立选择 UI | 复用摘要模型，只能改 `settings.json` 覆盖 | 用户无法在界面上给路由单独选小模型 |
| 路由缓存键不含 provider | 2 分钟内换 provider 仍命中旧建议 | 只影响少一次分类调用，不影响白名单 |
| 语义检索 | 只有 FTS5 关键词，同义改写命中不了 | “隔离配置”查不到“沙箱 ACL” |
| FTS `body` 冗余 | 正文在 FTS 表再存一份，磁盘约 3 倍 | 归档规模变大后需要外部内容表 |
| 索引实时性 | 只按行数判断，归档会话继续聊时索引会偏旧 | 搜索可能漏最新内容 |
| 撤销历史 | 只能撤回最近一次，没有 checkpoint 列表 | 多轮改动后无法选择性回滚 |
| checkpoint 磁盘 | 保留 20 份，大文件副本累积 | 大仓库长期使用会吃磁盘 |
| 外部修改检测 | 用户手改后徽标可能不提示 dirty | 验证门可能误报“已验证” |
| 摘要 token 成本 | 只在日志里，没进 `ContextReport` | 用户看不到压缩花了多少 |
| 数据库迁移 | 只做加列（AttachmentsJson / 摘要 / 轨迹 / 归档等），其它结构变更要手动 | 升级旧库有风险 |
| 图片附件内容 | 只给模型文件名 / 大小 / 路径 | 模型“看不到”图片内容 |
| 语法高亮 | 代码块只有等宽字体和底色 | 可读性 |
| Snap Layouts | 无边框自绘标题栏导致最大化按钮不出现贴靠布局浮层 | Windows 11 体验 |
| 双进程共用 SQLite | WPF 与 MAUI-Windows 同时写会 `database is locked` | 需要 `SDEMO_DATA_ROOT` 隔离 |
| 沙箱 trash 浏览 / 一键还原 | 只能到 `sandbox\trash\<jobId>\` 手动取回 | 删除后的找回体验 |
| Agent Plan 模型列表 | `/api/plan/v3` 无 `/models`，只能手动加 | 火山方舟套餐用户的接入摩擦 |
| 语言 | 只有简体中文，`en-US` 禁用 | 本地化未接入 |

### 3.7 其它已知限制（README 记录）

- 模型 BaseUrl 必须带 `/v1`（SDK 只拼 `/chat/completions`），只填域名时表单自动补全。
- API Key 用 DPAPI（当前用户）；换用户 / 换机器要重填。
- 不要在 WebView2 事件回调里同步弹模态框，会把消息循环重入导致闪退；文件夹选择器已改为 `Dispatcher.BeginInvoke`。
- MAUI 需要 workload；Android 还需要 JDK 17 + Android SDK。
- Android 没有托盘、没有“选文件夹”、没有自绘标题栏；窄屏侧栏改为顶部面板。
- 自定义搜索接口按 `Authorization: Bearer` + `{"query", "top_k"}` 调用；HTTP 200 但 `ResponseMetadata.Error` 会原样显示。

## 5. 结论

1. **功能面完成度很高**：基座、沙箱 S1–S6、插件 M0–M6、上下文 P1–P2、编辑 P3、内循环 P4、任务循环 P5、小模型 P6、能力路由 M1–M4 都有代码、单测和（多数）真机数据；最新回归是 Core 616 / Sandbox 214（1 跳过）。
2. **真正的短板不在“功能有没有”，而在“弱模型 + 8K + 外部仓库”**：P7 的 8K 只到 1/8，本地 32K 1/8；云端 32K 已 7/8，说明工具链可用，差距首先是模型档位。T05/T06/T07 的实现级验收（指定测试名 / 私有方法名）又放大了失败率。
3. **第二个短板是“验收深度”**：M1–M4 多数只到单测口径，30 工具 / 20 技能 / 20 条归档 / 8K 长任务都没真机复测；P1/P2/P5 的 UI 也没有自动化或像素走查。
4. **第三个短板是“产品化”**：无修改回灌、shrink guard、路由模型选择、语义检索、撤销列表等还停在评测或设计层。
5. **范围控制是主动的，不是遗漏**：多 Agent、LSP、向量 RAG、云端沙箱、自动 PR、插件市场等都在文档里明确写了“本期不做”及触发条件。

### 建议的下一步（按影响排序）

1. **把云端 32K 作为主档位**，本地 8B 只做单文件小改；8K 定位为“极短任务演示”，不要承诺中等重构。
2. **补丁链路**：`apply_patch` 按 hunk 上下文模糊定位 + 失败返回可复制候选补丁；工具失败返回非 `ok`，让循环保护能区分“被拒绝”和“成功”。
3. **任务与验收**：T05/T06/T07 改行为级断言；只读/测试类任务给文件范围提示；补测 T05 在 20–25 次工具预算下的表现。
4. **8K 专项**：减少定位成本（更宽松的 `search_files`、文件范围提示），或明确把 8K 目标下调为“单文件任务”。
5. **补验收**：M1–M4 各补一次真机规模化（30 工具 / 20 技能 / 20 归档 / 8K 长任务），P1/P2/P5 补 bUnit 或截图冒烟。
6. **产品化**：无修改回灌（最多 3 次）、路由模型选择 UI、checkpoint 列表、摘要成本进分解面板。
