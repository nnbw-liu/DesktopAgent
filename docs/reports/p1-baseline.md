# P1 基线：真实 token 计量与 8K 预算压测

> 目的：在开始 P1 之前，用真实模型量出「启发式估算 vs 服务端 usage」的误差，并验证「8K 模型 + 200 轮 + 50KB 附件」不再 400。
> 原始数据：[p1-baseline-data.json](data/p1-baseline-data.json)。复现工具：`tools/p1-baseline`（`dotnet run --project tools/p1-baseline -c Release`）。

## 1. 环境

| 项 | 值 |
| --- | --- |
| 操作系统 | Windows（用户本机） |
| 运行时 | .NET 10.0.401 |
| 本机推理 | LM Studio，`http://127.0.0.1:1234/v1` |
| 本机模型 | `qwen3.5-4b@q6_k`、`qwen3.5-9b@q6_k`、`qwen/qwen3.6-35b-a3b` |
| 云端 | 火山方舟 Agent Plan，`https://ark.cn-beijing.volces.com/api/plan/v3`，`deepseek-v4.1-flash` |
| 采样时间 | 2026-10-22 下午（Asia/Shanghai） |
| 采样方式 | 真实 HTTP 请求；`max_tokens = 32`；每条请求一次，不做重试 |

方法：

1. 用真实的 `ContextBuilder` 按 **8K 档**（`ModelProfilePresets.FromPreset("8K")`）组装请求，记录 `ContextReport.Estimated`。
2. 经过真实的 `ContextBudgetChatClient` 后，用 OpenAI 兼容的非流式接口发送，读取服务端 `usage.prompt_tokens`。
3. `误差 = (实际 - 估算) / 实际 × 100%`；正数表示估算偏高（低估 token），负数表示估算偏低（高估 token）。
4. 200 轮场景 = 200 组 user/assistant + 1 条当前输入；当前输入挂 50KB 纯文本附件。

> 说明：本机与云端模型的真实窗口都大于 8K（本机 32K/128K，云端 128K）。这里以 **8K 预算**模拟 8K 模型——请求大小由预算决定，服务端不会因为「模型窗口大」而放水；验收点是「在 8K 预算下请求确实很小且不 400」。

## 2. 短对话（10 轮，无附件）

| provider | model | 估算 | 实际输入 | 误差 | 总预算 | 耗时 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| local_lm | qwen3.5-4b@q6_k | 987 | 1002 | **+1.50%** | 4874 | 18.1s |
| local_lm | qwen3.5-9b@q6_k | 987 | 1002 | **+1.50%** | 4874 | 26.6s |
| local_lm | qwen/qwen3.6-35b-a3b | 987 | 1002 | **+1.50%** | 4874 | 67.0s |
| 火山 | deepseek-v4.1-flash | 987 | 965 | **−2.28%** | 4874 | 1.1s |

- 同一份请求在两家服务上的 usage 只差 3.7%（1002 vs 965），说明估算误差的主要来源是文本本身，不是厂商分词差异。
- 最大绝对误差 **2.28%**，远低于 15% 的验收线。

## 3. 8K 预算 + 200 轮 + 50KB 附件

| provider | model | 估算 | 实际输入 | 误差 | 保留轮次 | 省略消息 | 附件桩 | 结果 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | --- | --- |
| local_lm | qwen3.5-4b@q6_k | 575 | 634 | **+9.31%** | 4 / 201 | 394 | 是 | ✅ 200 |
| local_lm | qwen3.5-9b@q6_k | 575 | 634 | **+9.31%** | 4 / 201 | 394 | 是 | ✅ 200 |
| local_lm | qwen/qwen3.6-35b-a3b | 575 | 634 | **+9.31%** | 4 / 201 | 394 | 是 | ✅ 200 |
| 火山 | deepseek-v4.1-flash | 575 | 598 | **+3.85%** | 4 / 201 | 394 | 是 | ✅ 200 |

- **4/4 成功，无 400**。请求体从原始 26,085 字符（外加 50KB 附件）压到 587 字符。
- 若不做裁剪，乐观估算：26K 字符 ≈ 6.8K token、50KB 附件 ≈ 13K token、系统提示词 ≈ 0.9K token，合计 **≈ 20K token**，8K 窗口必然溢出。
- 裁剪后实际发出去约 600 token（预算上限 4874），留有充足余量。
- 附件被改成桩（`[附件已省略：50kb.txt, 50.0 KB, 路径]`），模型需要全文时仍可用 `read_file` 读取；这是 P1 的明确取舍，已写入 `p1-report.md`。
- 这一场景误差 +9.31%，比短对话大：裁剪后剩下的主要是中文正文，启发式对中文略偏保守（估算 575 < 实际 634）。仍在 15% 以内。

## 4. 校准

连续 4 次请求（`qwen3.5-4b@q6_k`，同一估算 691）：

| 次数 | 估算 | 实际 | 误差 | 请求时因子 | 请求后因子 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 | 691 | 692 | +0.14% | 1.000 | 1.0004 |
| 2 | 691 | 692 | +0.14% | 1.0004 | 1.0007 |
| 3 | 691 | 692 | +0.14% | 1.0007 | 1.0010 |
| 4 | 691 | 692 | +0.14% | 1.0010 | 1.0014 |

- 启发式在这组文本上已经足够准，EMA 因子稳定在 1.00 附近，没有出现漂移。
- 校准的价值在「偏差大」时体现（例如换分词器差异大的厂商）；其收敛、停用与重置逻辑由 `TokenCalibrationStoreTests` 固定，不在真机数据里强行制造偏差。

## 5. 结论

| 验收项 | 目标 | 实测 | 结论 |
| --- | --- | --- | --- |
| 每次请求有预算 | 全部请求 | ContextBuilder 统一产出，报告含 total/window | ✅ |
| 8K + 200 轮 + 50KB 附件不 400 | 不出现 400 | 4/4 请求 200，估算 575 ≤ 4874 | ✅ |
| 计量误差 | ≤ 15% | 最大 9.31%（短对话 ≤2.28%） | ✅ |
| 请求大小受控 | ≤ 输入预算 | 575 / 4874（11.8%） | ✅ |

已知限制：

- 本机没有真正的 8K 模型，8K 是「预算档位」而非物理窗口；若用户把 8K 档配在 128K 模型上，只会更保守，不会更危险。
- 50KB 附件不会全量内联；需要全文时依赖工具回读。
- 中途裁剪（工具循环内）没有在真机上单独压测：本机工具循环需要真实工具调用，基线只覆盖发送前；该路径由 `ContextBudgetChatClientTests` 与 `MidTurnPipelineSpikeTests` 固定。
